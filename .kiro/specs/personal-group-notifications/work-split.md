## 5. PR·병합 순서

1. S0: A의 1.1 PR을 가장 먼저 병합한다.
2. S1~S2: A(1.2, 1.3, 2.1, 2.2, 3.1, 3.3)와 B(4.1, 4.2)가 병렬 PR을 올린다. 같은 wave의 PR은 먼저 통과한 순서대로 병합하고, 나머지는 `main`을 rebase한 뒤 병합한다.
3. 이후 wave는 `tasks.md` 그래프 순서를 따른다. 태스크 PR은 선행 태스크가 `main`에 병합된 뒤에만 연다. 선행 PR이 리뷰 중이면 그 브랜치 위에 쌓지 않고 병합을 기다린다.
4. 기능 구현 PR에 해당 속성·통합 테스트 태스크가 있으면 같은 담당자가 바로 다음 PR로 올린다(예: 3.1 → 3.2).
5. 교차 의존 구간(wave 8~13)은 계약 타입 PR을 먼저 병합한다. 순서는 A 5.4·5.8 → C 7.7 → C 8.1·8.2 → B 9.1·9.3·10.1·10.5 → C 8.5 → B 9.6·10.7 → A 12.1 → C 11.1이다.
6. 한 PR은 하나의 태스크 또는 같은 wave의 밀접한 태스크 묶음(구현+테스트)만 담는다. PR 본문에 태스크 ID와 충족한 요구사항 번호를 적는다.
7. 병합은 squash가 아닌 일반 병합 또는 rebase로 하되 팀이 하나를 정해 일관되게 쓴다. `main`에 force push하지 않는다.

## 6. 공유 파일 충돌 방지 규칙

| 파일·영역 | 소유자 | 규칙 |
|---|---|---|
| `package.json`, `package-lock.json`, 루트 설정(`tsconfig`, ESLint, `next.config.ts`) | A | 의존성 추가는 A에게 요청하거나, B/C가 추가할 때는 해당 변경만 담은 소형 PR로 먼저 병합한다. lockfile 충돌은 `main` 기준으로 `npm install`을 다시 실행해 해결한다. |
| `prisma/schema.prisma`, `prisma/migrations/` | A | B, C는 직접 수정하지 않는다. 변경이 필요하면 이슈에 필요 필드와 근거를 적고 A가 마이그레이션 PR을 올린다. 마이그레이션 파일명 충돌을 피하려고 번호는 병합 직전에 확정한다. |
| 전역 CSS·디자인 토큰, `components/ui/*` | B | A, C는 새 컴포넌트가 필요하면 자기 도메인 폴더에 만들고 공통 컴포넌트는 수정하지 않는다. |
| `domain/schedule.ts`, `infrastructure/scheduler/*`, `instrumentation.ts` | C | A, B는 읽기만 한다. |
| `.github/workflows/*` | A | C의 13.5 단계 추가는 A가 병합 순서를 조율한다. |
| 라우트 폴더 | 3절의 책임 디렉터리 | 다른 담당자의 라우트 폴더에는 파일을 추가하지 않는다. |
| `tasks.md` | 전원(체크박스만) | 7절 규칙을 따른다. 태스크 내용, 순서, 그래프는 별도 PR로 합의 후 수정한다. |
| `requirements.md`, `design.md` | 전원(합의 후) | 구현 중 발견한 모순은 코드 PR에 섞지 않고 문서 PR로 분리한다. |

추가 규칙:
- 포매터·린터 일괄 변경이나 파일 이동은 별도 PR로 하며 다른 담당자의 열린 PR이 없을 때 병합한다.
- 같은 파일을 두 담당자가 동시에 수정해야 하면 먼저 PR을 연 사람이 파일을 소유하고, 다른 사람은 해당 PR 병합 후 rebase한다.
- 매일 작업 시작 전 `git fetch origin && git rebase origin/main`으로 브랜치를 갱신한다.

## 7. `tasks.md` 상태 공유와 중복 방지 규칙

- `tasks.md`의 체크박스 상태가 유일한 진행 기준이다. `[ ]` 미착수, `[-]` 진행 중, `[x]` 완료로 표시한다.
- 태스크를 시작할 때 담당자가 해당 줄을 `[-]`로 바꾸는 한 줄 PR(또는 첫 커밋)을 먼저 `main`에 병합한다. 이 표시가 없는 태스크는 아무도 시작하지 않은 것으로 본다.
- 3절 표에 없는 태스크는 하지 않는다. 다른 담당자의 태스크가 막혀 있어도 대신 구현하지 않고 이슈나 채팅으로 요청한다.
- 완료는 PR이 `main`에 병합된 뒤 `[x]`로 바꾼다. 하나의 PR 안에서 자기 태스크 줄만 수정하고 다른 줄은 건드리지 않는다.
- 상태 변경 PR과 코드 PR이 `tasks.md`에서 충돌하면 `main` 기준으로 자기 태스크 줄만 다시 적용한다.
- 담당 변경이 필요하면 이 문서를 수정하는 별도 PR로 합의한 뒤 진행한다. 임의로 남의 태스크를 가져가지 않는다.
- 태스크 진행 중 새 작업이 필요하면 `tasks.md`에 임의로 추가하지 말고 팀에 알려 합의 후 추가한다.

## 8. 브랜치 이름과 커밋 규칙

브랜치 형식: `<담당>/<태스크ID>-<짧은-설명>`. 예시:

- `a/1.1-project-init`, `a/2.1-prisma-auth-group-schema`, `a/5.4-group-membership-commands`
- `b/4.2-ui-components`, `b/6.1-compose-options-draft`, `b/9.3-confirm-dispatch`
- `c/7.1-schedule-calculator`, `c/8.1-claim-dispatch-transaction`, `c/13.5-quality-gate`

한 브랜치가 여러 태스크를 다루면 `a/3.1-3.2-validators-and-property-test`처럼 범위를 적는다. 브랜치 이름의 `.`가 불편하면 `a/t1-1-project-init`처럼 바꿔도 되지만 팀 안에서 하나로 통일한다. 커밋 메시지는 `feat(5.4): 그룹 멤버십 command 추가`처럼 태스크 ID를 접두어로 사용한다.

## 9. 완료 기준

태스크 완료는 다음을 모두 만족할 때다.

1. `tasks.md`의 해당 태스크 설명과 `_Requirements:_` 항목이 구현됐다.
2. 해당 태스크가 요구하는 테스트(속성 테스트는 `design.md`의 해당 Property 번호 주석 포함)가 통과한다.
3. PR에서 `npm run lint`, `npm run typecheck`, `npm test`가 통과한다. 통합·E2E 태스크는 `npm run test:e2e` 또는 PostgreSQL 통합 테스트까지 통과한다.
4. 다른 담당자의 소유 파일을 수정하지 않았거나, 수정했다면 소유자의 승인을 받았다.
5. 최소 한 명의 다른 담당자가 리뷰하고 승인했다.
6. `main`에 병합된 뒤 `tasks.md`가 `[x]`로 갱신됐다.

프로젝트 완료 기준은 13.5의 단일 품질 게이트(lint, typecheck, 단위·속성·통합·E2E, axe, visual regression, production build)가 `main`에서 통과하고, `requirements.md`의 수용 기준 추적표 1~9의 테스트가 CI 결과에 모두 존재하는 것이다.

## 10. 위험과 확인 사항

- wave 11~13은 세 담당자가 서로의 산출물을 소비하므로 지연이 전파된다. 5절 5번의 병합 순서를 우선 지킨다.
- B의 분량이 가장 많다. 10.x가 지연되면 11.x를 맡은 C가 먼저 공통 상태 컴포넌트 점검을 시작할 수 있으며, 이때도 B의 파일은 수정하지 않는다.
- 이 분할은 `tasks.md`의 그래프만 근거로 새로 정리했다. 이전 점검 결과 문서는 이 작업에서 참조하지 못했으므로 차이가 있으면 팀 합의 후 이 문서를 수정한다.
