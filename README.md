# 했냥
친구나 그룹에 알림을 보내고, 누가 '확인' 버튼을 눌렀는지 발송 회차별로 보여주는 알림 서비스예요.

**Demo:** https://dviy4c2kvl7qw.cloudfront.net

---

## 1. 문제 정의

### 대상 사용자
친구, 연인, 가족, 동료처럼 서로 할 일을 챙겨 주는 사람들이에요. 일대일로 쓸 수도 있고, 가족이나 팀처럼 여럿이 함께 쓸 수도 있어요.

### 문제 상황
서로 할 일을 챙길 때 "약 먹었어?", "오늘 약속 기억해?" 같은 확인 메시지를 메신저로 매번 보내요. 상대가 메시지를 읽어도 실제로 했는지는 다시 물어야 알 수 있어요. 매일이나 매주 반복되는 일이면 같은 질문을 계속 반복하게 돼요.

### 기존 방식과 한계
- **메신저:** 채팅방에 들어오기만 해도 읽음으로 바뀌어서 확인 여부를 알 수 없어요. 확인 질문은 대화에 묻히고, 반복되는 일은 매번 다시 보내야 해요.
- **개인 할 일 앱:** 본인만 체크할 수 있어서, 상대가 했는지는 볼 수 없어요.

### 근거
팀원 3명이 직접 겪은 사례예요.

- **연인 사이의 약속 확인:** 데이트 약속이 있는 날, 한 팀원은 아침마다 "오늘 약속 있는 거 기억해?"라고 메시지를 보내고 "ㅇㅇ 기억해"라는 답을 받았어요. 같은 질문을 약속이 있을 때마다 직접 보내야 했고, 답이 늦게 오면 기억하는지 알 수 없었어요.
- **어머니 복약 확인:** 한 팀원은 어머니가 약을 드셨는지 확인하려고 매일 전화나 메시지로 물어봤어요. 메시지를 읽으셔도 실제로 드셨는지는 다시 여쭤봐야 알 수 있었어요.

두 사례 모두 같은 질문을 반복해서 보내고, 상대가 답해야만 확인 여부를 알 수 있었어요. 했냥은 이 질문을 반복 알림으로 한 번만 등록하고, 상대가 '확인' 버튼을 누르는 것으로 답을 대신해요.

### 목표
- 수신자가 '확인' 버튼을 눌러야만 확인으로 기록해요. 앱에 들어오거나 알림을 읽는 것만으로는 상태가 바뀌지 않아요.
- 반복 알림도 회차마다 수신자와 응답을 따로 기록해서, 발신자가 이번 회차 미확인자를 바로 찾을 수 있게 해요.
- 그룹 기록은 현재 구성원이 가입한 이후의 회차만 볼 수 있게 해서 기록 노출 범위를 제한해요.

## 2. 핵심 기능
| 기능 | 해결하는 불편 | 코드 위치 |
|---|---|---|
| Google 로그인 | 별도 가입 절차 없이 바로 시작해요 | |
| 이메일로 친구 추가 | 개인 알림을 보낼 대상을 관리해요 | |
| 그룹 생성과 초대 링크 | 친구가 아닌 사람도 링크 수락만으로 그룹에 모여요 | |
| 개인 발송 / 그룹 발송 (둘 중 하나만 선택) | 알림마다 받는 대상이 분명해요 | |
| 반복 알림 (매일·매주·매월, 주말 제외) | 정기 알림을 매번 다시 쓰지 않아도 되고, 주말 회차는 다음 평일로 옮겨져요 | |
| 회차별 받은 알림 카드와 '확인' 버튼 | 읽기만 한 것과 실제 확인한 것을 구분해요 | |
| 회차별 응답 현황 | 이번 회차에서 누가 아직 확인하지 않았는지 봐요 | |
| 가입 시점 기반 조회 권한 | 가입 전 기록과 탈퇴 후 기록이 노출되지 않아요 | |
| 그룹별 이메일 공개 설정 | 기본은 닉네임만 보이고, 공개를 고른 그룹에서만 이메일이 보여요 | |

## 3. 사용 시나리오
1. 엄마가 '우리 가족' 그룹을 만들고 초대 링크를 가족 채팅방에 공유해요. 아빠와 딸이 링크를 열고 수락해서 구성원이 돼요.
2. 엄마가 "저녁 약 챙겨 먹기" 알림을 매일 저녁 9시 반복으로 한 번만 등록해요.
3. 딸은 받은 알림 목록에서 오늘 회차 카드를 보고, 약을 먹은 뒤 '확인' 버튼을 눌러요. 아빠는 카드를 보기만 해서 '미확인'으로 남아요.
4. 엄마는 응답 현황에서 오늘 회차를 골라 "확인 1/2"를 보고, 아빠에게만 따로 연락해요.
5. 다음 날 회차는 두 사람 모두 '미확인'으로 새로 시작해요. 어제 기록은 어제 회차에 그대로 남아요.

## 4. 기대 효과
| 항목 | 기존 (메신저) | 했냥 |
|---|---|---|
| 매일 반복되는 할 일 알림 작성 | 한 달에 30번 직접 보냄 | 처음 1번만 등록 |
| 수신자 3명에게 확인 여부 묻기 | 회차마다 최대 3번 따로 물어봄 | 응답 현황 1번 조회 |
| 실제로 했는지 판단하는 기준 | 읽음 표시 (열기만 해도 바뀜) | 확인 버튼을 누른 사람과 시각 |

## 5. 차별점
- **명시적 확인:** 메신저 읽음 표시와 달리 '확인' 버튼을 눌러야만 기록돼요.
- **회차별 기록:** 반복 알림의 응답이 회차마다 분리돼서 지난 회차 응답과 섞이지 않아요.
- **발송 시점 기준 수신자:** 그룹 발송의 수신자는 실제 발송 시점의 구성원으로 정해지고, 이미 발송된 회차는 그 목록을 유지해요.
- **가입 기간 기반 권한:** 늦게 가입한 사람은 이전 회차를 볼 수 없어요. 탈퇴하면 본인이 보낸 알림을 포함해 그룹의 모든 기록을 볼 수 없어요.

## 6. 설치와 실행
### 준비물
- Node.js 26 (배포 환경과 같은 버전)
- Supabase 프로젝트 (로그인은 Supabase Auth, 데이터는 Supabase PostgreSQL)
  - migration이 Supabase의 `auth.users` 테이블을 참조하므로 일반 PostgreSQL에는 적용되지 않아요.
- Google OAuth 클라이언트 (Client ID와 Secret은 Supabase 대시보드의 Google provider에 넣어요)
- 리디렉션 URL 등록 위치와 값은 [`docs/deployment.md`](docs/deployment.md) 4절에 있어요. 로컬 개발에는 Supabase Redirect URLs에 `http://localhost:3000/auth/callback`을 추가해요.

### 환경 변수
레포 루트에 `.env.local` 파일을 만들고 아래 값을 채워요. 이 파일은 커밋하지 않아요.

```bash
# 앱 런타임: Supabase Transaction pooler (포트 6543)
DATABASE_URL="postgresql://postgres.<project-ref>:<password>@<region>.pooler.supabase.com:6543/postgres?pgbouncer=true"
# migration 전용: 포트 5432 연결 (직접 연결 또는 Session pooler)
DIRECT_URL="postgresql://postgres.<project-ref>:<password>@<region>.pooler.supabase.com:5432/postgres"
APP_BASE_URL="http://localhost:3000"
NEXT_PUBLIC_SUPABASE_URL="https://<project-ref>.supabase.co"
NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY="sb_publishable_..."
```

`sb_secret_…`나 `service_role` 키는 넣지 않아요. 배포 환경에 넣는 변수는 [`docs/deployment.md`](docs/deployment.md)에 정리했어요.

### 실행
```bash
# 1. 의존성 설치
npm ci

# 2. 데이터베이스 스키마 적용 (Prisma CLI는 .env.local을 자동으로 읽지 않아요)
set -a && . ./.env.local && set +a && npx prisma migrate deploy

# 3. 개발 서버 실행 (http://localhost:3000)
npm run dev
```

프로덕션 모드로 실행하려면 `npm run build` 후 `npm start`를 실행해요. 프로덕션 모드에서는 시작할 때 환경 변수를 검사하고, 발송 스케줄러가 30초마다 예약된 회차를 보내요.

## 7. 테스트
```bash
npm run lint                 # 정적 검사
npm run typecheck            # 타입 검사
npm run test:unit            # 단위·속성·컴포넌트 테스트
npm run test:integration     # PostgreSQL 통합 테스트 (Docker 필요, Testcontainers가 DB를 띄워요)
npm test                     # 위 두 테스트를 함께 실행
```

통합 테스트는 실제 PostgreSQL에서 예약, 발송 회차 생성, 동시 발송 중복 방지, 확인 응답, 그룹 가입 시점 기반 조회 권한을 검증해요.
